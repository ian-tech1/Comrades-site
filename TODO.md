## Payment, receipts, reconciliation and records hygiene update (2026-11-22)

- [x] **Automatic downloadable receipts for learners and admins.** For every fully confirmed paper/results/refer payment, automatically make a downloadable PDF receipt available to both the paying learner and admins. The receipt must include the linked request/service, registered website-account identity, M-Pesa receipt code, amount, payer phone, payer name only when actually verified, and transaction date/time with its source clearly indicated. Learners can download only their own receipts; admins can download every receipt. Regression tests verify receipt ownership/status gates and PDF provenance fields.
- [x] **Reliable, evidence-based payment capture.** Store payer phone, receipt, amount, Safaricom transaction time, callback event, confirmation method and reconciliation status. Accept callback confirmation only when complete matching evidence is present. Surface callback gaps, mismatches and provider status results for reconciliation; never mark payment successful from a status query alone. Do not label an STK-prompt phone number as the payer's registered name. Allow an admin to record payer name only after checking M-Pesa proof, and mark that identity source as administrator-verified. Callback gaps remain operationally recoverable; the system does not guarantee zero missed provider callbacks.
- [x] **Manual reconciliation and review queue.** Let an administrator refresh/query pending STK transactions, review failed/mismatched/unmatched callback cases, and record a missed-callback payment only with the receipt code, exact amount, payer phone, and manually verified transaction time/name when available. Every verification is audit logged and duplicate receipt codes remain blocked.
- [x] **Safe cleanup and archive controls.** Provide request/payment archive, restore and show-archived controls to keep the default screens concise. Preserve successful payment rows and their receipts as immutable financial history; do not hard-delete confirmed payments. Permit hard deletion only for an unpaid request with no payment attempts, subject to ownership/admin checks and a durable deletion audit. Archive/restore changes are attributed to the acting account. v16.5.2 locks and checks unpaid deletion in one database transaction and uses a restrictive payment FK; v16.5.3 serializes request archive/restore with new payment-attempt insertion, atomically checks active attempts, and writes the archive audit in the same transaction.
- [x] **Refresh and start-fresh controls.** Add a visible transaction refresh, periodic refresh while the transaction screen is open, last-updated feedback, and one-click clearing of filters/search without erasing records. “Start fresh” clears visible filters/search only; it does not erase portal records.
